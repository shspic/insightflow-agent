# InsightFlow Agent 面试问答

## 1. 你这个项目是做什么的？

这是一个多模态文档与数据分析智能体项目。用户可以上传 CSV、Excel、PDF、图片等文件，然后用自然语言创建任务，比如分析表格、生成图表、查询 PDF 内容、识别图片文字、生成 Markdown 报告。系统会根据任务类型调用不同工具，并展示最终结果和执行轨迹。

## 2. 为什么这个项目算 Agent，而不是普通 CRUD 系统？

普通 CRUD 主要是增删改查固定数据。这个项目的核心是任务执行：系统会理解用户输入，判断任务类型，生成计划，选择工具，执行数据分析、PDF 检索、OCR 或报告生成，然后整理结果并记录每一步轨迹。它具备“任务判断 + 工具调用 + 结果生成 + 过程可观测”的 Agent 链路。

## 3. LangGraph 在项目里起什么作用？

LangGraph 用来把 Agent 执行流程显式建模成节点工作流。当前工作流是线性的，包括 `classify_task`、`plan_task`、`route_tools`、`execute_tool`、`write_result`、`save_result`。这样比把逻辑写在一个大函数里更清晰，也方便记录每个节点的输入、输出、状态和耗时。

## 4. Agent 的工作流是怎么设计的？

我把一次任务拆成六个步骤：先分类，判断是数据分析、图表、PDF 问答、OCR、报告还是多文件综合分析；然后生成计划；再根据任务类型选择工具；接着执行工具；最后把工具结果整理成中文回答，并保存任务状态和执行轨迹。这个流程现在是确定性的，便于演示和调试。

## 5. 你为什么没有一开始就接大模型 API？

我先做本地工具能力和工作流闭环。原因是如果一开始就接 LLM，很容易变成聊天壳，文件处理、数据分析、RAG、OCR 这些核心能力反而不稳。先用规则和模板打通链路，可以保证无 API Key 也能运行，后续再让 LLM 做增强，而不是让系统依赖 LLM 才能工作。

## 6. 接入 LLM 后，它在系统里负责什么？

LLM 只做增强，不替代安全工具。它可以辅助模糊任务分类、生成更自然的计划、基于工具结果组织最终回答、基于检索片段生成 PDF 问答，以及优化报告结论。它不能执行用户代码，不能删除文件，也不能编造工具结果中没有的数据、页码或图表。

## 7. 你的 RAG 是怎么实现的？

PDF 上传后先用 PyMuPDF 提取文本，再按页切分成 chunk，保存到 `file_chunks` 表。检索时从数据库取出 chunk，根据用户问题做关键词或轻量 TF-IDF 检索，返回相关片段、页码、文件名和分数。document_qa 任务会基于这些片段生成带引用来源的回答。

## 8. PDF 检索为什么先做关键词 / TF-IDF，而不是一开始上 Chroma / FAISS？

这是为了保证项目轻量、稳定、可部署。Chroma、FAISS、sentence-transformers 会增加依赖体积和部署复杂度，而当前演示版重点是把 RAG 链路跑通，包括分块、检索、引用来源和 Agent 调用。TF-IDF 足够展示检索流程，后续生产化可以替换为向量数据库。

## 9. 图片 OCR 是怎么实现的？

图片 OCR 使用 pytesseract + Pillow。系统从配置读取 `TESSERACT_CMD` 和 `OCR_LANG`，如果配置了 Tesseract 路径就显式设置；如果本机或部署环境没有 Tesseract，服务会捕获异常并返回中文提示，不会让后端崩溃。识别结果会保存到 `files.summary` 和 `schema_json.ocr_result`。

## 10. 数据分析工具是怎么保证安全的？

数据分析只调用预设 Pandas 函数，例如读取 CSV / Excel、统计行列数、字段类型、缺失值、数值列统计和文本高频值。系统不接受用户输入的 Python 代码，也不让 LLM 生成代码后执行，所以不会出现用户通过自然语言执行任意代码的问题。

## 11. 为什么不执行用户输入的 Python 代码？

因为这是很高风险的设计。用户输入代码可能读取本地文件、删除数据、访问环境变量或执行系统命令。这个项目的定位是安全可控的 Agent 演示，所以只允许调用预设工具函数，用工具参数驱动分析，而不是执行用户代码。

## 12. 执行轨迹有什么价值？

执行轨迹能解释 Agent 做了什么。比如一次任务会记录分类结果、执行计划、选择了哪些工具、工具输入输出、耗时和错误。这样前端不只是展示最终答案，还能展示系统推理和工具调用过程，对调试、面试演示和排查失败原因都很有价值。

## 13. 项目中最难的部分是什么？

最难的是把不同能力统一到一个任务系统里。CSV / Excel 是表格分析，PDF 是文本分块和检索，图片是 OCR，报告又要整合前面的结果。同时还要记录 Agent 每个节点轨迹，保证没有 API Key 或 OCR 环境缺失时系统仍能降级运行。

## 14. 部署时遇到了什么问题？

主要遇到三类问题：一是 Docker 构建时 Debian 源拉取 Tesseract 失败，所以 Docker 版先把 OCR 作为可选能力；二是 Render 使用动态 `PORT`，启动命令必须写成 `--port $PORT`；三是 Vercel 前端和 Render 后端跨域，需要正确配置 `VITE_API_BASE_URL` 和 `CORS_ORIGINS`。

## 15. Render / Vercel 免费部署有什么限制？

Render 免费服务会冷启动，首次访问可能较慢；Render 免费 Web Service 的本地文件系统不适合长期保存 SQLite 数据库和上传文件；OCR 依赖运行环境，不一定可用；Vercel 环境变量修改后需要重新部署才会生效。所以这个部署适合演示，不是生产级方案。

## 16. 如果让你继续优化，你会做什么？

我会先把 SQLite 升级为 Postgres，把本地 storage 升级为对象存储；然后把 RAG 从 TF-IDF 升级为 Chroma 或 FAISS；再增加用户登录、任务隔离、异步任务队列和更完整的测试评估体系。最后可以增强多文件跨文档问答和 PDF / DOCX 报告导出。

## 17. 这个项目和普通 ChatGPT 套壳有什么区别？

普通套壳通常只是把用户输入发给模型再显示回复。这个项目的核心是工具执行：上传文件后，系统会真实解析文件、做 Pandas 分析、生成 Matplotlib 图表、提取 PDF、执行 OCR、生成报告，并记录每一步工具调用。LLM 只是可选增强，不是系统唯一能力。

## 18. 你在项目中主要负责哪些内容？

我主要负责从需求拆解、后端 API、数据库模型、文件处理、Agent 工作流、RAG、OCR、报告生成、前端页面、Docker、本地与公网部署，到 README 和面试文档整理的端到端实现。这个项目的重点是工程闭环，而不是单点算法。

## 19. 如果面试官问“代码都是 AI 写的吗”，应该怎么回答？

可以坦诚说：我在开发中使用了 AI 编程助手提高效率，但项目不是简单复制生成代码。我负责需求拆解、架构取舍、阶段划分、调试验证、部署排错和最终集成。每个阶段我都限定范围，比如先做本地工具能力，再接 LLM，再做部署，并处理了 CORS、Tesseract、Render 环境变量等实际工程问题。

## 20. 这个项目对 AI 应用开发岗位有什么价值？

它展示了 AI 应用开发中很核心的能力：文件输入、工具调用、Agent 编排、RAG 检索、LLM 降级、执行轨迹、前后端联调和部署上线。它不是生产级系统，但覆盖了 AI Agent 项目从需求到演示的主要工程环节，适合用来证明我具备把 AI 能力落到实际应用里的能力。
