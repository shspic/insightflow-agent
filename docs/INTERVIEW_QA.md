# InsightFlow Agent 面试问答

## 1. 你这个项目是做什么的？

这是一个多用户多模态文档与数据分析 Agent 平台，当前版本为 `3.0.2`。V3 工程投标审查主线使用确定性抽取、规则引擎、DeepSeek Verification、MCP 工具、BM25+BGE+RRF 混合检索、四节点 Supervisor 和 Quality Gate 生成可核验报告；V2 通用线保留五类文件理解、任务计划、独立 Worker、SSE 和三格式报告。项目已通过 IP 地址证书完成单机 HTTPS 公网部署。

## 2. 为什么这个项目算 Agent，而不是普通 CRUD 系统？

普通 CRUD 主要是对固定数据增删改查。当前 V3 主线更准确的定位是**受控的工作流型 Agent**：

- 确定性 Review Pipeline 先完成材料抽取和规则检查，模型不能绕过业务规则；
- Verification Agent 在预检通过后规划固定 MCP 工具，并结合 BM25+BGE+RRF 检索核验证据；
- 四节点 Supervisor 按 `extraction → verification → quality_review → reporting` 推进结构化状态；
- Quality Gate 校验来源哈希、定位信息和输入快照，不满足条件时阻止报告交付；
- 模型调用、工具调用和重试都有边界，执行过程可以追踪和复核；
- 候选结论需要人工确认，系统没有包装成完全自主的多 Agent 协作。

V2 兼容线另有 Supervisor、计划确认和五个专业步骤，不能把这套旧链路写成 V3 当前主链。项目之所以不只是 CRUD，是因为它把模型决策限制在可追踪的任务状态、工具边界和质量门控之内，形成“抽取—核验—审查—交付”的闭环。

## 3. 为什么从 V1 单 Agent 改成 V2 Supervisor + 子 Agent？

V1 使用 LangGraph 固定线性工作流（分类、计划、路由、执行、整理、保存），在单文件单任务时能跑通，但存在几个根本问题：

1. 任务分类和工具选择耦合在一起，多文件综合分析需要硬编码分支；
2. 不能追问——发现信息不足只能继续执行，无法停下来让用户补充；
3. 计划无法确认——生成和执行在同一个 HTTP 请求里完成，用户只能接受结果；
4. 没有独立质量审核——报告无数字校验、引用验证和自动修复。

V2 做了三个核心改变：把"理解需求+调度"交给 Supervisor，把"专业执行"拆成五个子 Agent，在报告交付前增加独立的 Quality Review。这样每个 Agent 只做一件事、边界清晰、可独立调试，出问题时能定位到具体 Agent 和步骤。

## 4. 子 Agent 如何划分职责边界？

按职责边界划分，不按文件类型划分：

1. **File Understanding Agent**：理解文件内容，输出摘要、角色建议、标签和文件关系候选。输入是元数据和解析结果，输出是受 schema 约束的 Profile。不分析数据、不写报告。

2. **Data Analysis Agent**：确定性表格分析。做缺失值/重复值/分布/分组/连接/对比/趋势统计，生成图表规格。不解释 PDF 规则，不写报告。

3. **Document Research Agent**：PDF/Markdown 事实检索。输出事实列表和带页码/章节的引用。不计算表格数字，不生成报告。

4. **Report Agent**：综合所有上游输出为结构化报告。把分析结果、文档事实、图表引用整合为统一中间结构，可渲染为 Markdown/DOCX/PDF。不重新计算数字，不编造引用。

5. **Quality Review Agent**：交付前独立质量审核。检查结构完整性、数字一致性、引用有效性、计划完成度。最多两轮审核和受限自动修复。

## 5. 为什么 OCR、解析、图表、导出是工具而不是 Agent？

因为它们有明确输入、确定性接口和可校验输出，没有独立目标、长期上下文或决策收益。把它们包装成 Agent 会额外引入 Prompt、状态同步、重试和模型成本，却不能提高结果质量。工具负责"按参数执行并返回结果"，Agent 决定"是否需要、需要什么参数"，确定性编排器负责权限、超时和状态。

## 6. 如何避免无限循环？

系统使用多层防护，所有预算在执行前写入执行快照：

- 追问最多 2 轮，每轮最多 3 个问题；
- Supervisor 计划生成最多 2 次（初稿 + 用户修改后重整）；
- 每个专业 Agent 每个步骤默认 1 次模型调用，语义修订最多 1 次；
- 单步骤自动重试最多 1 次，单任务自动重试步骤总数最多 2 个；
- Quality Review 最多 2 轮，第二轮后仍不通过则标记 completed + 质量警告，不再循环；
- 标准任务模型调用总上限 12 次，超过上限前停止并给出降级结果或明确失败；
- 确定性编排器在每次模型调用前后检查预算。

## 7. 计划确认有什么意义？

计划确认是安全和用户体验的双重保障：

- 用户在正式执行前看到系统会使用哪些文件、做哪些步骤、预期产出什么，可以修改或取消；
- 避免模型误判任务意图后在用户不知情的情况下完成错误分析并产生模型费用；
- 计划版本化保存，确认记录和修改历史全部可审计；
- 从计划重新执行时固定原计划版本和输入文件快照，保证可复现。

## 8. 数据库队列为什么不用 Celery？

项目面向 5 人以内低并发单机部署。使用 Celery 需要额外部署 Redis/RabbitMQ，增加运维复杂度，且 Celery 的进程模型和 Windows 兼容性对当前场景过于复杂。数据库队列（使用 `available_at`、`lease_owner`、`lease_expires_at` 和租约机制）在低并发时足够可靠：Worker 轮询领取、租约到期后可被重新领取、崩溃不丢任务。业务层通过队列接口抽象，未来可切换到专业队列后端。

## 9. SQLite 单 Worker 适用什么边界？

适用：约 5 人以内、低并发写入、任务按队列顺序执行、单机部署。SQLite 开启 WAL 模式后读可并发，但写是库级锁，单 Worker 串行执行避免了写冲突。

不适用：多机多实例并发写、高频繁并发、需要消息优先级或延迟消息。超过边界时应迁移到 PostgreSQL + 专业队列。

## 10. SSE 如何恢复断线？

1. 浏览器原生 EventSource 自动重连，携带 `Last-Event-ID` 请求头；
2. 后端从数据库 `task_events` 表查询该 ID 之后的事件并补推；
3. SSE 不可用时前端自动降级到 2-5 秒增量轮询（通过 `after_id` 参数）；
4. 任务到达终态后清理 EventSource 和定时器。

## 11. 取消为什么是协作式？

用户调用取消接口后，数据库写入 `cancel_requested_at`。等待中的任务立即变更为 cancelled。正在执行的任务，Worker 在确定性检查点（步骤开始前、工具调用前后、模型调用后、文件循环中）主动检查并响应。

已发出的外部 HTTP 调用（如 DeepSeek API）无法从客户端强制终止，只能靠超时或 API 客户端支持的取消。这不是设计缺陷，而是分布式系统基本原则——已发出的网络请求无法从客户端强制撤销。

## 12. 局部重试如何工作？

以失败 `task_step` 为单位：失败步骤创建新 attempt，复用未失效的上游步骤结果（通过数据库持久化的产物引用），当前步骤及下游标记为待重新计算。工具使用幂等键（`idempotency_key`）避免重复生成资产。Quality Review 发现可修复问题时触发目标步骤重试，最多重试 2 个不同步骤。

## 13. 文件关系为什么需要用户确认？

文件关系（如"两张表可以按某列连接"、"Excel 受 PDF 规则约束"）直接影响后续分析正确性。如果连接键错误，全部合并/对比/汇总结果都失真。系统自动生成的候选包含置信度和证据，但：

- confidence 是启发式阈值不是真实概率；
- 模型可能误判字段含义；
- 涉及连接键、覆盖更新、规则约束的关系，即使高置信也需用户确认。

低置信度关系默认不参与自动分析。

## 14. RAG 如何保证引用？

两条主线需要分开讲。V2 通用分析线把 PDF 按页提取并分块，使用关键词/TF-IDF 返回带页码和 chunk ID 的片段；引用 ID 必须解析到真实记录。V3 工程审查线按 PDF 页、Excel 行区间和 Markdown 分节构建确定性 Corpus，使用 BM25+BGE+RRF 混合检索；检索命中只形成候选证据，人工采纳前服务端重新校验 locator、内容哈希和文件归属。Quality Gate 再复算 Evidence、来源文件与 input snapshot，不能解析或哈希不一致的引用不得进入报告。当前主线不是“只用 TF-IDF”。

## 15. Quality Review 如何防止数字和引用错误？

Quality Review Agent 做七项检查：报告结构完整性、数字与工具输出一致性、引用 ID 可解析性、引用覆盖性、计划步骤完成度、资产文件存在性、语义一致性（DeepSeek 辅助）。可自动修复的（如数字不符、缺少章节但上游数据存在）触发目标步骤重试；不可自动修复的（如文件损坏、需用户确认连接键）标记为警告并交付。

## 16. DeepSeek 不可用如何降级？

三层降级：一是确定性功能（文件解析、Pandas 分析、图表生成、OCR、报告模板渲染）完全不依赖 DeepSeek，即使 API 完全不可用也能输出结构化结果；二是 DeepSeek 调用有连接超时、读取超时和最大重试限制，失败时记录降级标记并继续执行；三是 deterministic 评估集（85 条）完全不调用 DeepSeek，验证系统非 LLM 部分正确性。旧模型名触发 degraded readiness 但不伪装成功。生产环境通过 `DEEPSEEK_MODEL_DEFAULT` 和 `DEEPSEEK_MODELS_AVAILABLE` 环境变量配置模型名。

## 17. 用户数据如何隔离？

每一层都做归属校验：工作区查询用 `workspace.owner_user_id = current_user.id`，文件操作用 `file.owner_user_id` + `workspace_file.workspace_id` 双重校验，任务/报告/下载/SSE/取消/重试逐级校验 `task.owner_user_id` 和 `workspace.owner_user_id`。管理员默认不返回普通用户报告正文、文件内容和脱敏模型输入。依赖层提供可复用的权限依赖，不每个路由手写校验。

## 18. Session Cookie 和 CSRF 机制？

认证使用服务端不透明 Session Token：登录成功后生成高熵随机 token（`secrets.token_urlsafe`），数据库只保存 `token_hash`（SHA-256），浏览器通过 `HttpOnly`、`Secure`（生产）、`SameSite=Lax` Cookie 携带。修改密码/管理员重置/账号停用时撤销所有 Session。CSRF 使用双 Token 模式：Session Cookie 之外服务端下发一个可读的 CSRF Token，前端在状态变更请求中通过自定义 Header 回传，后端逐请求校验。

## 19. 报告版本和三格式导出？

任务完成后自动生成初始报告（version 1）。用户选择新模板、提交纠错反馈或修改参数后，系统生成递增版本的新报告，旧版本保留。三格式导出：Markdown（直接返回正文）、DOCX（python-docx 生成）、PDF（Markdown 经渲染引擎转换）。导出文件作为 `report_assets` 保存，通过鉴权下载接口获取，不暴露服务器路径。

## 20. 配额和监控系统？

配额系统：用户级（存储量、单文件大小、单次上传文件数、每日任务数、并发任务数），管理员免普通配额但不免系统级安全上限，API 层逐请求检查。

监控系统分四层：Worker 级别（运行状态、心跳、租约）、Agent 级别（任务总数、成功/失败/取消、平均耗时）、工具级别（调用总数、成功/失败、平均耗时）、模型级别（调用次数、Token 用量、错误率）。三层健康检查：浅层 `/api/health`、含数据库 `/api/health/readiness`、含 Worker 心跳 `/api/health/live`。

## 21. deterministic 评估代表什么？

85 条 deterministic 评估覆盖文件解析、任务意图分类、工具路由、文件角色建议和报告模板选择。**它明确不代表 DeepSeek 模型准确率。**它是确定性规则与预期路由的自检：验证系统的非 LLM 部分（文件类型判断、工具选择、角色推断规则、报告模板匹配）是否按设计工作。当前 `task_success_rate=1.0`、平均响应 1ms，说明确定性路由全部命中——验证的是代码正确性，不是模型表现。评估集完全不调用 DeepSeek。

## 22. 国内部署方案？

使用 Docker Compose + Nginx 同域方案：`web`（Nginx + React 静态产物，80/443）反代 `/api` 到 `backend`，独立 `worker` 与 `mcp` 服务共享受控持久数据。关键配置包括 SSE 无缓冲、SPA fallback、安全头、上传限制、SQLite WAL、非 root/只读根文件系统，以及部署、备份、升级和回滚脚本。当前实例为 <https://43.153.181.237/>，部署事实与待办见 `docs/DEPLOYMENT_V3.md`；`docs/V2_07_*` 只作为 V2 历史材料。

## 23. 当前最大限制？

当前关键限制：

1. 已通过 IP 地址证书公网部署，但尚无域名、ICP/公安备案，`public_launch_enabled` 仍为 false；
2. 公网只完成匿名页面与健康检查验收，登录后的上传、核验、MCP、报告和跨用户隔离尚未形成当前版本的全链自动化记录；
3. 已完成真实 DeepSeek+BGE+MCP 评测，但 validation recall@3=0.6429、no-answer FP 率=1.0，不能声称模型或 RAG 高准确率；
4. SQLite 单 Worker 只适合低并发，未迁移 PostgreSQL、对象存储或专业队列；
5. 文件理解仍有同步 HTTP 路径，未支持任意 Agent 节点暂停/恢复，也不能强制撤回已经发出的外部调用；
6. V3 已使用 BM25+BGE+RRF 混合检索；TF-IDF 仅属于 V2 历史事实，不能再代表当前工程审查主线；
7. 后端当前收集 959 项，但本轮完整重跑未在 300 秒内完成，不能写“959 项全部通过”；
8. 当前为单机部署，没有高可用与故障切换验证；现有 Git Tag 为 `v3.0.2`，但匿名线上接口尚未暴露 build version，仍需发布标识证明部署 commit。

## 24. 代码是否由 AI 辅助？

诚实回答：在开发中使用了 AI 编程助手提高效率。但我负责需求拆解和阶段划分（V2-01 到 V2-08）、关键架构决策（Supervisor + 子 Agent 职责划分、数据库队列 vs Celery 取舍、取消/重试语义设计）、每一阶段的验证标准制定和实际测试执行、调试排错（CORS、CSRF、Tesseract、Docker 构建、Pandas 警告、datetime 弃用），以及文档整理。AI 编程助手是工具，项目架构、取舍、验证和交付由我把控。

## 25. 本人在项目中的真实职责

我负责从需求分析、架构设计、数据库迁移、后端 API、Agent 工作流、RAG、OCR、文件处理、报告系统、前端页面、Docker 部署、运维脚本到文档整理的端到端实现。每个阶段限定范围、先验证再推进。项目的重点是工程闭环：不是单点算法或模型效果，而是从用户注册到最终报告交付的完整系统。
