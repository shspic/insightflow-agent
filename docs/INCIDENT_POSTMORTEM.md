# Git 对象库事故复盘（Incident Postmortem）

> 目的：区分触发行为、直接原因与根因；不把责任归给单一命令；为同类事故提供可执行的防复发清单。

## 1. 事故概要

在开发过程中，仓库 `.git/objects` 中的大量对象丢失，导致本地细粒度提交历史部分缺失。经恢复后，所有工作区文件与关键内容通过 SHA-256 与测试双重验证，项目继续推进（后续 6A/6B/6C 各阶段均在此基础上完成）。

## 2. 因果分层（必须区分）

| 层次 | 内容 | 判定 |
| --- | --- | --- |
| **Trigger（触发）** | 执行了 `git stash push`（Git 官方标准命令，用于暂存未提交改动） | 事实 |
| **Direct cause（直接原因）** | 在同一时间窗内，`.git/objects` 目录被递归清扫（对象文件被删除/清空），使已提交与暂存对象失去引用 | 事实（目录内容缺失被观测到） |
| **Root cause（根因）** | 具体执行删除操作的进程**未被日志确认**，无法唯一归因到某条命令或脚本 | **undetermined（无法确定）** |

**重要澄清**：标准 Git `stash push` 本身**不会**删除对象——stash 只是把改动打包成提交对象并恢复工作区。本项目对象丢失发生在 `stash` 与递归清扫同一时间窗，但没有任何证据表明 stash 命令删除对象；根因判定为 undetermined，不做未经证实的归因。

## 3. 恢复过程

1. 立即**停止一切写操作**（不 commit、不 gc、不 prune、不 checkout 覆盖）；
2. 从远端健康仓库执行 **clone 恢复**（重新拉取全部分支与标签）；
3. 将恢复后的健康 clone 作为新的工作仓库；
4. 把工作区未提交内容与恢复仓库逐项核对；
5. 用测试套件做功能级验证（见第 4 节）。

## 4. 量化验证

| 验证项 | 结果 |
| --- | --- |
| 关键文件 SHA-256 | 与恢复前记录一致（内容无丢失） |
| 恢复时后端测试 | **611 项通过** |
| 恢复时前端测试 | **76 项通过** |
| 恢复后完整测试 | 持续通过（6A 阶段 791 后端 + 103 前端；6B 浏览器冒烟 3 passed；6C CI 冒烟 4 passed） |

## 5. 最终损失

- 部分**本地细粒度提交历史**（小步提交的中间 commit 信息）丢失；
- 工作区文件、关键成果、远端历史**无损失**（经 SHA 与测试双重验证）。

## 6. 防复发清单

1. **阶段 commit/push**：每个可验证的阶段结束即提交并推送，避免长周期不落地的改动堆积；
2. **禁止 Agent 操作危险 Git 命令**：`stash`、`gc`、`prune`、`repack`、`clean`、`reset`、`restore`、`checkout --` 等由人工在受控环境执行；自动化任务默认只读；
3. **健康 clone**：恢复与日常开发使用完整 clone（含全部对象），不用浅克隆做正式工作仓库；
4. **定期 `git fsck --full`**：作为完整性检查纳入阶段验收；
5. **离线备份**：关键阶段对仓库目录做整目录备份（不依赖 Git 内部格式）；
6. **最小权限**：删除/清扫类操作与开发操作分属不同进程/账户，且删除操作必须记录日志（本次根因未定的直接原因即删除进程无日志）。

## 7. 与后续工作的关系

本次事故后建立的约束（只读预检、禁止 stash/clean/reset 等、阶段验收含 fsck）已在 6A/6B/6C 各阶段执行并保持有效；`git fsck --full` 在每次阶段预检与终检均通过。
