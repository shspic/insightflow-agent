# InsightFlow Agent 简历材料

## 项目名称

InsightFlow Agent：多模态文档与数据分析智能体

## 一句话项目描述

基于 FastAPI + React + LangGraph 构建的多模态文档与数据分析 Agent 平台，支持文件上传、表格分析、PDF 检索问答、图片 OCR、图表生成、Markdown 报告生成和 Agent 执行轨迹展示。

## 简历 Bullet

- 设计并实现多模态文档与数据分析 Agent 平台，基于 FastAPI、React、SQLite 和 LangGraph 构建“文件上传 → 任务分类 → 工具调用 → 结果生成 → 执行轨迹展示”的完整闭环。
- 实现 CSV / Excel 解析与 Pandas 数据分析能力，支持字段识别、缺失值统计、数值列描述性统计、文本高频值统计和前 5 行数据预览。
- 实现 PDF RAG 初版能力，基于 PyMuPDF 提取 PDF 文本并切分 chunk，通过轻量检索返回相关片段、页码和引用来源。
- 实现图片 OCR 与 Markdown 报告生成模块，支持将 OCR 结果、表格分析、图表和 PDF 引用整合为可下载报告。
- 设计 Agent 可观测执行轨迹，记录 `classify_task`、`plan_task`、`route_tools`、`execute_tool`、`write_result`、`save_result` 等节点的输入、输出、状态、耗时和错误，提升调试和演示可解释性。

## 技术栈关键词

- 前端：React、Vite、JavaScript
- 后端：FastAPI、Uvicorn、Pydantic
- 数据库：SQLite、SQLAlchemy
- 数据分析：Pandas、openpyxl
- 图表：Matplotlib
- PDF：PyMuPDF
- OCR：pytesseract、Pillow、Tesseract OCR
- Agent：LangGraph、工具调用、执行轨迹
- 工程化：Docker、Docker Compose、Markdown 文档

## 面试时 1 分钟介绍话术

InsightFlow Agent 是我做的一个多模态文档与数据分析智能体项目。它不是普通聊天机器人，而是面向真实文件的任务执行系统。

用户可以上传 CSV、Excel、PDF 或图片，然后输入自然语言任务，比如“分析这个文件的数据概况”“生成图表”“这份 PDF 里有哪些关键内容”“识别这张图片里的文字”“生成分析报告”。后端通过 LangGraph 工作流完成任务分类、计划生成、工具路由、工具执行、结果整理和保存。

这个项目的重点是完整闭环和可观测性：前端能提交任务并展示结果，后端会调用 Pandas、Matplotlib、PyMuPDF、OCR、报告生成等工具，并把每个 Agent 节点的输入、输出、状态、耗时和错误写入 `tool_calls` 表，前端可以展示完整执行轨迹。

当前版本是单用户本地演示版，不夸大为生产系统。它更适合展示 AI Agent 应用开发、工具调用编排、文件处理和后端工程能力。

## 这个项目为什么是 Agent？

它具备 Agent 项目的核心执行链路：

- 接收自然语言任务。
- 根据输入和文件类型判断任务类型。
- 生成执行计划。
- 路由到合适工具。
- 调用预设工具完成数据分析、图表生成、PDF 检索、OCR 或报告生成。
- 整理工具结果并返回中文答案。
- 记录每一步执行轨迹，支持前端查看。

当前版本不是开放式聊天 Agent，而是确定性规则驱动的任务型 Agent。这个取舍让系统更安全、更可控，也更容易展示每一步工具调用。

## 为什么没有一开始接 LLM API？

没有一开始接 LLM API 是有意取舍：

- 第一阶段优先保证文件上传、解析、分析、图表、RAG、OCR 和报告生成这些基础工具能力真实可用。
- 规则分类能覆盖当前演示任务，成本低、稳定、可解释。
- 不接入 LLM 可以避免 API Key 泄露、调用成本、网络不稳定和不可控输出。
- Agent 架构已经预留了分类、计划和结果整理节点，后续可以逐步把这些节点替换或增强为 LLM 驱动。

面试时可以说明：这个项目先把工具链和工作流打通，再接入 LLM，这比先做一个聊天壳更工程化。

## 项目难点是什么？

1. 多类型文件处理链路统一
   - CSV / Excel、PDF、图片的处理方式完全不同，需要统一到文件表、任务系统和前端展示中。

2. Agent 执行过程可观测
   - 不只是返回最终答案，还要记录每个节点的输入、输出、状态、耗时和错误，并在前端展示。

3. 工具调用安全性
   - 数据分析不能执行用户输入代码，只能调用预设 Pandas 函数。
   - OCR、PDF、报告生成都不能删除或修改原始上传文件。

4. 本地演示稳定性
   - Docker 启动、SQLite 数据、本地存储、OCR 配置都要处理好边界情况。
   - Docker 演示版默认不强制内置 Tesseract，避免系统包下载失败影响主功能启动。

5. 报告整合
   - Markdown 报告需要整合任务、文件、分析、图表、PDF 引用和 OCR 结果，同时不能破坏原有任务流程。

## 后续如何增强？

- 接入 LLM，用于更灵活的任务分类、计划生成和结果总结。
- 将 PDF RAG 从轻量检索升级为向量数据库，例如 Chroma 或 FAISS。
- 支持多文件综合分析和跨文件问答。
- 支持 DOCX / PDF 报告导出。
- 增加用户登录、权限管理和任务隔离。
- 增加后台任务队列，处理更大的文件和更长任务。
- 增加自动化测试和评估集，验证 Agent 工具调用稳定性。
- 部署到云端，提供可访问的公网演示环境。

## 面试中可以主动说明的限制

- 当前是单用户本地演示版，不是生产级 SaaS。
- RAG 初版优先使用关键词或轻量检索，不是生产级向量检索系统。
- OCR 依赖本机或容器环境中的 Tesseract 配置。
- 当前没有复杂多轮记忆和用户权限系统。
- 当前没有编造公网部署地址；如果需要展示线上版，需要后续真实部署。
